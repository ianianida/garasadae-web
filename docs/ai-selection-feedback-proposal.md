# AI 개입 범위와 피드백 수집·개선 설계

> 2026-10-01: 초기 ② 방식 확정, ③은 검증 후 확장 후보. 상세 설계는 공동 검토 중이며 앱·AI 연결·배포는 아직 구현하지 않았다.

## 확인된 요구와 제안의 경계

- 확인된 요구: 배포 후 사용자 피드백을 효과적으로 수집하고 뽑기 알고리즘을 신속하게 개선한다.
- 확인된 운영 방식: **서비스는 피드백을 데이터로 수집·내보내고, 사용자는 그 자료를 Codex에 전달해 함께 분석·개선한다.** 개선용 AI는 서비스에 직접 넣지 않는다. 개선 자동화 문항 이후 사용자가 이 역할을 명확히 정정했다.
- 확인된 개입 범위: **초기에는 ② 고민 해석만 AI를 사용한다.** AI가 선택지·양쪽 부담·명시된 제약·불확실한 조건을 구조화하고, 검수된 사례 데이터·규칙으로 말씀 후보·가중치·추첨을 결정한다.
- 확장 후보: **③ 고민 해석과 말씀 후보 평가까지 AI**. 실제 사용자 반응을 비교해 효과를 확인한 뒤 함께 확장한다. 자동 확장이나 임의의 통과 수치는 정하지 않았다.
- 검토 중인 상세 설계: 고민 해석 출력 형식·AI 공급자, 데이터와 규칙의 연결 방식, 피드백 화면·자료 형식, 품질 기준과 구체적인 검증·전환 절차.
- 유지하는 기준: 사용자가 말씀에서 운명적인 적합함과 선택의 실마리를 발견해 후련해지는 경험. 서비스가 행동 결론이나 하나님의 명령을 선언하지 않는다.

## 초기 ② 방식의 뽑기 흐름

1. 뽑기 요청에 고유 ID를 만들고 처리 상태를 저장한다. 같은 요청의 재전송은 중복 뽑기와 중복 평가로 집계하지 않는다.
2. AI에 고민 원문을 전달해 선택지·양쪽 부담·명시된 제약·불확실한 조건을 구조화한다. 표현이 달라도 같은 갈등을 읽을 수 있도록 하며, 입력에서 확인할 근거가 없는 속마음은 확정하지 않는다. 말씀 후보와 후보별 점수는 AI 입력·출력에 포함하지 않는다.
3. 서버가 정해진 형식과 필수 조건에 맞는 해석 결과인지 확인하고, 고민 원문과 연결되는 근거를 저장한다. AI의 해석은 사용자 자신의 확정된 판단과 구별한다. 필드와 검증 규칙은 공동 결정한다.
4. 검수한 `구체 고민 × 말씀` 사례·적용 조건을 해석 결과와 규칙으로 대조해 후보를 찾는다. 직접적인 주제뿐 아니라 선택의 갈등에 자연스럽게 연결되는 관점도 포함한다. 조건이 다른 실패 사례를 구별한다. 초기 후보 평가·배제·가중치 계산은 검수된 데이터와 코드 규칙이 수행한다.
5. 서버가 정한 후보와 추첨 설정으로 한 구절을 뽑는다. 후보 수와 확률을 포함한 설정을 버전별로 보존한다. 균등 또는 가중 추첨의 구체 선택·가중치·통과 기준은 공동 결정한다. 품질이 낮은 후보를 다양성 확보 목적으로 자동 추가하지 않는다.
6. 선정한 구절의 원문·역본·출처를 데이터베이스에서 가져와 표시한다. 맞춤 해석이나 행동 판정의 생성은 이 제안에 포함하지 않는다.
7. 표시한 결과와 선정 기록을 저장한다. 새로고침으로 뽑기를 다시 실행하지 않는다. 결과 주소는 접근 권한으로 보호하고, 공유는 별도 제품 결정에 따른다.

초기의 런타임 AI 개입은 고민 해석이다. ③에서 후보 본문·문맥을 AI에 전달해 후보별 적합성을 평가하는 절차는 별도 확장 항목으로 둔다. 임베딩·의미 검색도 모델을 사용하는 추가 개입이므로 초기 방식에 자동 포함하지 않는다.

AI 호출 실패·시간 초과에는 버전이 정해진 기존 선정 방식으로 대체하는 후보를 검토한다. 대체 여부와 원인을 기록해 정상 AI 뽑기의 성능과 구별한다. AI 공급자와 응답 시간·비용 한도는 미결정이다.

## ③ 확장의 검토 방식

- 비교 대상: 같은 고민 유형에서 ②와 ③이 만드는 첫 뽑기의 실제 사용자 경험.
- ③의 추가 개입: 초기 규칙으로 찾은 후보의 실제 본문과 검수한 문맥을 AI가 평가하고, 그 결과를 후보 자격 또는 순위에 반영하는 방식. AI가 만든 점수는 만족 확률로 간주하지 않는다.
- 살필 결과: 자기 상황에 꼭 맞는 느낌·뜻밖의 연결·사용자가 읽은 선택의 실마리·후련함과 실패 이유. 응답 수·응답률·비용·지연을 함께 살핀다.
- 확장 판단: 실제 반응에서 이점이 확인되는지 공동 검토한다. 비교 방식·최소 근거·통과 기준은 아직 정하지 않았다.

## 피드백 화면 후보

말씀을 읽고 사용자가 반응할 수 있는 시점에 선택 사항인 한 번의 응답을 제공한다.

> 이번 뽑기는 어땠나요? → 딱 맞아요 / 애매해요 / 아쉬워요

선택 후 추가 이유는 선택 사항으로 제안한다.

| 반응 | 이유 버튼 후보 |
|---|---|
| 좋았음 | 내 상황 같음 / 뜻밖의 연결 / 선택의 실마리 / 후련해짐 |
| 아쉬움 | 연결되지 않음 / 뜻이 어려움 / 선택의 실마리가 없음 / 뻔하거나 재미없음 |

자유 의견은 선택 사항이다. 문구와 표시 시점은 화면을 보며 함께 정한다. 강제 설문으로 뽑기 경험을 완성해야 하는 구조는 제안하지 않는다.

한 줄 기록을 남긴 행위·재뽑기·이탈·공유는 보조 신호다. 저장했다는 이유만으로 만족을 확정하거나, 응답하지 않았다는 이유만으로 실패를 확정하지 않는다. 일기 문장을 개선에 활용하는 범위·동의와 원문 보관·삭제 기준은 공동 결정한다.

## 함께 저장할 데이터 후보

| 기록 | 목적 |
|---|---|
| 고민 ID, 뽑기 ID, 시도 순서, 상태, 결과 표시 시각 | 한 고민의 첫 결과와 재뽑기 및 실제 결과 노출을 구별 |
| 사용자 또는 임시 세션 ID | 같은 사람의 중복 반응과 실험 집계를 구별; 로그인 전제는 아님 |
| 고민 원문·AI가 추출한 선택지·양쪽 부담·명시 제약·불확실한 조건 | 해석 오류와 후보 데이터·규칙 문제를 구별; 접근 및 보관 범위는 공동 결정 |
| 구절·역본 ID와 본문 데이터 버전 | 실제로 읽은 원문과 현재 본문을 구별 |
| 후보 ID, 적용한 사례·조건·규칙과 채택·탈락 근거 | 초기 후보 데이터와 규칙 중 어느 단계가 문제인지 진단 |
| 최종 구절 ID, 추첨 확률, 후보군·가중치 설정 | 추첨을 포함한 선정 조건 추적 |
| 해석 모델·프롬프트·규칙·사례 데이터·알고리즘 버전 | 변경 원인을 비교하고 기존 설정으로 되돌리기 |
| 실험 배정과 배정 확률 | 비교할 사용자 집단과 노출 조건 확인 |
| 피드백 값·이유·선택 의견·수정 시각 | 실제 반응을 특정 뽑기에 연결; 중복 제출은 별도 표로 유지하거나 갱신 |
| 모델 사용량, 비용 추정, 단계별 지연, 대체 처리 여부 | 품질·응답 속도·운영 비용을 함께 비교 |

개인 기록은 권한으로 보호하고, 운영 지표는 집계 중심으로 본다. 실패 원문 사례에 접근할 수 있는 주체, AI 제공자에 전송할 범위, 공유·삭제 기준은 실제 데이터 수집 전에 결정한다.

## 수집한 자료로 함께 개선하는 흐름

### 같은 고민에서의 대응

재뽑기를 제공하기로 정한 경우, 직전 구절을 제외하는 방식과 피드백 기록을 연결한다. 아쉬웠다는 반응만으로 구매·포기 중 사용자가 원하는 결론을 추측하지 않는다. 실패 이유를 선정에 활용하는 구체 규칙은 자료 분석 후 함께 결정한다.

### 전체 서비스의 개선

1. 서비스가 피드백을 구체 고민·구절·선정 버전에 연결한다. 응답 수와 결과 노출 수를 함께 기록한다. 서비스 내 수집·집계·자료 내보내기에는 개선용 AI를 사용하지 않는다.
2. 사용자가 수집 자료를 내보내 Codex에 전달한다. 관계가 있는 기록을 연결할 수 있는 JSON과 집계용 CSV를 형식 후보로 검토한다. 포함할 원문·개인정보·접근 범위는 함께 결정한다.
3. 이 대화에서 Codex가 반복 실패와 근거를 분석하고 사용자가 검토한다. 예: 일시적인 조급함을 다루는 구절이 실제 비용 제약을 가진 고민에 반복 노출됐는지 확인한다. 서비스에 AI 분석 기능이나 자동 개선 작업을 추가하는 단계는 없다.
4. 후보 검색 범위, 사례 조건, 제외 조건, 추첨 가중치, 고민 해석 AI의 프롬프트 중 수정 대상을 함께 정한다. 한 사람의 부정 평가만으로 구절을 모든 고민에서 제외하지 않는다. ③ 확장 여부는 실제 반응을 비교해 별도로 판단한다.
5. 결정한 변경을 코드·데이터·설정의 새 버전으로 만들고 Git에 기록한다. 기존 사례와 별도 검증 사례에서 비교한다. 과거에 다른 구절을 받았다면 어떤 반응이었을지는 이 평가만으로 알 수 없다.
6. 검증한 변경을 배포하거나 버전 설정으로 전환한다. 필요하면 일부 이용자에게 기존 버전과 나누어 제공해 첫 결과의 실제 평가, 피드백 응답률, 고민 유형별 차이, 지연·비용을 비교한다. 비율·기간·최소 근거·중단 기준은 공동 결정한다.
7. 다음 수집 자료에서 변경의 영향을 함께 확인한다. 나빠진 경우 이전 버전으로 되돌릴 수 있도록 이전 설정과 기록을 보존한다.

확실한 원문·출처 오류의 후보 제외는 운영 화면에서 빠르게 처리할 수 있는 별도 기능 후보다. 주관적인 만족도 개선과 같은 자동 규칙으로 다루지 않는다.

운영 방식은 **서비스에서 수집·내보내기 → 사용자와 Codex가 자료 분석·수정 → 검증·새 버전 적용**이다. 서비스 내 AI 실패 분류·개선안 생성·모델 재학습·자동 프롬프트 교체는 넣지 않는다. 초기 뽑기의 AI 개입은 ② 고민 해석으로 정했고, ③ 후보 평가는 검증 후 확장 후보로 둔다.

## 운영 화면의 최소 후보

- 첫 뽑기 반응 분포, 응답 수·노출 수·응답률, 실패 이유, 결과 지연·비용.
- 구체 고민·구절·버전별 반복 실패와 성공 사례. 표본 수가 적은 조합은 별도로 표시.
- 기간·선정 버전·첫 뽑기 여부별 자료 내보내기. 각 기록이 연결되도록 ID를 포함.
- 함께 결정한 변경 이력과 운영 중인 버전 확인.
- 기존·새 설정 비교와 일부 실험·전환·복구는 운영 화면 또는 Codex 작업 흐름 중 적절한 위치를 공동 결정한다. 초기 AI 해석 결과와 실제 사용자 평가를 구별한다. ③의 후보 평가를 시험할 경우 그 기록도 구별한다.

## 평가에서 구별할 것

- 주된 목표 후보는 첫 뽑기의 좋은 경험이다. 구매·보류 어느 방향인지 자체에는 점수를 주지 않는다.
- 피드백 응답자 만족과 전체 이용자의 만족을 구별하고, 응답하지 않은 사람의 반응은 미확인으로 남긴다.
- 재뽑기 감소·기록 증가를 단독 성공 기준으로 사용하지 않는다. 재뽑기 감소가 이탈 때문인지 살핀다.
- 한 사람의 여러 재뽑기·반복 제출이 여러 독립 사용자의 평가처럼 집계되지 않도록 한다.
- 사전 사례 검수와 실제 사용자 피드백을 서로 다른 데이터로 저장한다. ③을 시험할 때의 모델 평가도 별도로 기록하고, 모델 점수가 좋아진 것만으로 배포 품질 개선을 선언하지 않는다.
- 이전에 노출하지 않은 구절의 사용자 반응은 아직 모른다. 기록된 노출 확률을 이용하는 비교에도 후보 범위와 충분한 표본 등 조건이 필요하다.
- 데이터가 적을 때 작은 수치 차이를 개선으로 단정하지 않는다. 불확실성과 고민 유형별 차이를 함께 보고 전환 기준을 정한다.

## 단계적으로 만들 제안

1. 검수한 구절·사례 데이터에 AI 고민 해석 결과를 연결하는 ② 기본 선정 방식을 구체화한다. 출력 형식·적용 조건·추첨 설정은 공동 결정한다.
2. 첫 배포부터 뽑기 기록·가벼운 피드백·기본 집계·자료 내보내기를 포함한다.
3. 사용자가 자료를 Codex에 전달해 함께 분석하고 새 선정 버전을 검증·적용한다.
4. 실제 반응이 쌓인 뒤 ③ 후보 평가의 비교 실험과 확장 기준을 함께 정한다. 서비스 내 개선용 AI는 넣지 않는다.

## 설계 참고 자료

- [Supabase 벡터 열](https://supabase.com/docs/guides/ai/vector-columns): 의미 검색을 추가로 검토할 때의 참고 자료이며 초기 ②에 채택한 기능은 아니다. 본문이나 사례의 의미 유사도는 좋은 뽑기 만족도와 구별한다.
- [Vercel Flags](https://vercel.com/docs/flags/vercel-flags): 설정 전환·일부 배포·비교 실험을 위한 기술 후보. 채택·비용은 미결정이며 자체 설정 테이블도 비교할 수 있다.
- [추천 알고리즘의 과거 기록 기반 평가 연구](https://arxiv.org/abs/1003.5956), [노출 확률을 기록한 데이터의 학습 연구](https://arxiv.org/abs/1901.04723): 실제 제공한 결과의 반응만 알 수 있다는 한계와 노출 조건 기록의 중요성을 참고한다. 연구 결과가 가라사대의 만족도를 입증하는 것은 아니다.
